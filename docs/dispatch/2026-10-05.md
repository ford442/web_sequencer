### B. GitHub issue — draft now (Copilot prep)

```markdown
Title: feat(drums): sample-accurate drum trigger offsets inside the render quantum (drumkit-processor)

## Context / motivation
`src/audio-worklets/drumkit-processor.ts` queues `trigger` messages carrying `audioTime` (`DrumTriggerQueue`, `src/audio-worklets/drumkit/triggerQueue.ts`) and drains them once per `process()` call at the block's `currentTime`, then renders the whole 128-frame quantum with one `drumkit_process(handle, numFrames)` call. Every hit is therefore quantised to the start of a render block: up to 2.9 ms of jitter at 44.1 kHz, worse at larger quanta, and audibly loose on hats and flams. Owner epic #1344 ("shared C++ voice core with sample-accurate events — 303 worklet ignores note audioTime, drums are block-quantized") names this; owner issue #1363 lists a `drumKitSchedule.ts` + test from an abandoned worktree as the first piece worth salvaging. This issue is that slice, re-implemented from `main`, and nothing else from the epic.

Active focus areas this touches: WASM pipeline stability (the native drum path) and the hybrid engine's native tier. It does not touch the rubberband/TTS worklet, the 303 worklets, types, workflows, or the lint baseline.

## Proposed approach (first pass — Noah will expand)
1. New pure module `src/audio-worklets/drumkit/drumKitSchedule.ts`:
   - `frameOffsetFor(audioTime, blockStartTime, sampleRate, blockFrames)` → integer in `[0, blockFrames)`; negative/overdue triggers clamp to 0, triggers beyond the block are not due.
   - `splitBlock(triggers, blockStartTime, sampleRate, blockFrames)` → ordered list of `{ frameStart, frameEnd, triggersAtStart[] }` segments covering the whole block.
   - Unit tests (Vitest, hermetic, no WASM): offset math at 44.1k/48k/96k, multiple hits in one block, same-frame coalescing, overdue clamp, block boundary (offset == blockFrames belongs to the next block).
2. In `drumkit-processor.ts#process()`: replace the single drain + single `drumkit_process(numFrames)` with: for each segment, apply its triggers (`applyTrigger`), then call `drumkit_process(handle, segmentFrames)` and copy that many frames into the output at `frameStart`. `drumkit_process` already takes `numFrames`, so no C++ change is expected; verify it accepts any `numFrames <= bufferSize` and that the returned pointer is valid per call.
3. Keep the fast path: a block with zero or one trigger at frame 0 must execute exactly the code it executes today (one native call, no extra allocation). Preallocate the segment list; no per-block GC on the audio thread (the repo's Bolt rules).
4. `DrumTriggerQueue.drain` grows a variant that drains triggers due within `[blockStart, blockStart + blockFrames / sampleRate)` with their offsets, instead of only `<= currentTime`.
5. Main-thread side (`src/engines/DrumKitEngine.ts`, `playDrum.ts`): confirm `audioTime` is the scheduler's intended hit time, not `currentTime` at send. If it is already, no change.

## Acceptance criteria (rough)
- [ ] `drumKitSchedule.ts` + `drumKitSchedule.test.ts` exist; tests pass in `CI=true pnpm run test:unit`.
- [ ] Two triggers 1.5 ms apart inside one 128-frame block at 48 kHz render at different frame offsets (integration test with the real `hyphon_native.wasm`, `HYPHON_REQUIRE_NATIVE=1`), not at frame 0.
- [ ] A block with no triggers performs one `drumkit_process` call (assert via a spy in the unit test harness).
- [ ] No new allocations in `process()` on the steady-state path (document how it was checked).
- [ ] `pnpm exec tsc -b`, `pnpm lint`, `pnpm run lint:ratchet`, `CI=true pnpm run test:integration` green; `scripts/check-module-size.mjs` still OK (drumkit-processor.ts stays under 700 lines).
- [ ] Docs: one paragraph in `docs/audio-engine/drumkit.md` describing sub-block scheduling and the fast path.

## Open questions for Noah
- Does `drumkit_process` in `emscripten/drumkit_wrapper.cpp` tolerate consecutive calls with `numFrames < bufferSize` inside one quantum (internal envelope/oscillator state advances per frame, not per call)? If not, this needs a tiny C++ change and a native rebuild — in scope or a follow-up?
- Should `applyTrigger` for a same-frame kick + open-hat choke keep today's ordering (choke after trigger)?
- Is per-hit pan (also in #1363) worth folding in here, or a separate issue? (Recommendation: separate.)
- Should the 303 worklet's `audioTime` handling (the other half of #1344) reuse `drumKitSchedule.ts`? Naming matters if yes.
```
