# Holographic Knob Renderer — Performance Audit

## src/components/MagicKnob.tsx — findings

### GPU Resource Lifecycle
- **Adapter/Device acquisition**: Happens inside a `useEffect` → `init()` async closure. Every mounted instance calls `navigator.gpu.requestAdapter()` and `adapter.requestDevice()` independently. **No sharing** across instances.
- **Pipeline creation**: `device.createShaderModule()` + `device.createRenderPipeline()` are executed per-instance inside `init()`. The WGSL string is embedded inline and recompiled for every knob. **No pipeline cache**.
- **RAF loop start**: `init().then(() => render())` chains pipeline creation to RAF registration. The loop begins as soon as the async init resolves.
- **RAF loop stop**: On unmount, `cancelAnimationFrame(animationId)` is returned from the effect. **No IntersectionObserver, no Page Visibility API, no CSS `display:none` detection**. The loop runs continuously while mounted, even if off-screen.
- **Cleanup completeness**: The effect cleanup only cancels the RAF. **No `device.destroy()`, no `context.unconfigure()`, no buffer destruction**. The `GPUDevice`, `GPUBuffer`, `GPURenderPipeline`, and canvas context are left for GC. This is a memory leak risk, especially if knobs are mounted/unmounted frequently.

### RAF Loop Count (Simultaneous)
If 6 MagicKnob instances were mounted, **6 independent `requestAnimationFrame` loops** would be running. Each fires its own `render()` callback every display frame (~60–165 Hz).

### Shader & Draw Call Cost
- **Canvas size**: `width={size * 2}` × `height={size * 2}`. Default `size=100` → 200×200 px. Not responsive to `devicePixelRatio`, so it appears blurry on HiDPI screens despite over-rendering 2× logical size.
- **Redraw policy**: **Unconditional**. The `render()` function writes `performance.now() / 1000` to the `time` uniform every frame and submits a new render pass. There is **no dirty-check** — it redraws even when `valueRef.current` is static.
- **Shader complexity**: Fragment-heavy WGSL with:
  - Per-pixel `rotate()` matrix construction (`sin`, `cos`, `mat2x2f`)
  - `atan2` calls for dash ring and arc angle tests
  - `smoothstep` branching for ring, arc, circle edge, inner glow, beam, vignette
  - Needle projection math (`dot`, vector subtraction, `length`) per pixel
  - Bloom divisor `1.0 / (perp * 100.0)` with a branch guard
  - Glitch branch (`step` + conditional UV offset)
  - ~15–20 ALU operations per fragment + several branch divergences
  - At 200×200 = 40k fragments × 6 knobs = 240k fragments/frame. Manageable on desktop dGPU, but wasteful on integrated GPUs / mobile.

## src/components/Knob.tsx — findings

### CSS/SVG Reflow Risk
- **Animated properties**: `transform: rotate(${rotation}deg)` with `transition: isDragging ? 'none' : 'transform 0.3s ease-out'`.
- **Reflow surface**: `transform` is **compositor-only**; it does **not** trigger layout, paint, or reflow in the main thread. The browser promotes the inner knob div to its own layer.
- **No layout thrashing**: The component does not read/write interleaved layout properties (e.g., `offsetHeight`, `clientWidth`). All geometry is CSS-driven.

### Memoization & Render Efficiency
- **Wrapped in `React.memo`** (line 16). Props are shallow-compared.
- **Callback stability**: `handleMouseMove` and `handleMouseUp` are wrapped in `useCallback` with dependency arrays that include `isDragging`, `dragStartY`, `dragStartValue`, `min`, `max`, `step`, `onChange`, `logarithmic`. This is **over-subscribed** — any parent re-render that passes a new `onChange` reference (even if functionally identical) invalidates the callback and can cause `useEffect` churn in the drag listener attachment.
- **Local state**: `isDragging`, `dragStartY`, `dragStartValue` are `useState` inside the component. Dragging one knob only re-renders that specific instance, not siblings.
- **Value update path**: `onChange(newValue)` is called from `handleMouseMove` on every mouse-move event while dragging. If the parent does not memoize `onChange`, this can cascade re-renders up the tree. In practice, `SynthPart.tsx` and `DrumMachine.tsx` use `useCallback` for handlers, so the blast radius is contained.

### Reflow Surface at Scale
With 20+ Knob instances on screen:
- Each knob is a composited layer during transition (when `isDragging` flips to `false` and the `transform` animates back).
- No layout recalculation is forced.
- The main cost is **React reconciliation** of 20+ component nodes + **layer management** overhead, not reflow.

## src/utils/knobConfigs.ts — findings

- Pure generator functions that map param objects to `KnobConfig[]` arrays.
- `getSynthControls` creates **12** config objects per call.
- `getKickControls` creates **4**, `getSnareControls` creates **4**, etc.
- These arrays and objects are **re-created on every call** (new references). Without a stable wrapper (like `useStableKnobConfig`), downstream `React.memo` comparisons on `controls` arrays will always fail.
- `valueDisplay` strings are concatenated inline, producing new strings every call.

## src/hooks/useStableKnobConfig.ts — findings

- Implements deep-equality memoization by comparing individual `KnobConfig` fields (`id`, `value`, `x`, `y`, `size`, `label`, `isRecording`, `valueDisplay`).
- If a field changed, only that config object is replaced; others keep stable references.
- **Used in `useAppState.tsx`** for `HardwareModule` controls (`synthAControls`, `synthBControls`, `bass2Controls`, etc.).
- **NOT used in `SynthPart.tsx` or `DrumMachine.tsx`**. Those components receive raw `params` objects and compute values inline inside `Knob` props. Therefore, `Knob` instances in SynthPart/DrumMachine do not benefit from config-object stability — but they also don't consume config objects, so `useStableKnobConfig` is irrelevant there.
- The hook's purpose is satisfied for `HardwareModule`, but it is **dead code for the primary Knob.tsx usage sites**.

## Bottleneck Report

### 1. 🔴 MagicKnob: Per-instance GPU device + pipeline + RAF (Impact: CRITICAL)
**Severity**: Highest  
**Evidence**: Each instance calls `requestAdapter()` → `requestDevice()` → `createShaderModule()` → `createRenderPipeline()`. With 6 instances, 6 adapters, 6 devices, 6 compiled pipelines, 6 RAF loops.  
**Cost**: Shader compilation is blocking on the GPU process; device creation consumes memory (~MBs per device). RAF loops burn CPU/GPU cycles unconditionally.  
**Scope**: Currently **zero** production impact because `MagicKnob` is **orphaned** (not imported anywhere). Risk is latent — if a future feature mounts even one instance, the cost is immediate.

### 2. 🔴 MagicKnob: Unconditional RAF redraw with no dirty-check (Impact: HIGH)
**Severity**: High  
**Evidence**: `render()` writes `performance.now()` to the time uniform and submits a command buffer every single frame, even when `valueRef.current` has not changed. No `requestAnimationFrame` throttling or visibility gating.  
**Cost**: ~40k fragments × N instances × 60–165 Hz = millions of wasted fragment executions per second. On battery-powered devices this directly drains power.

### 3. 🟡 MagicKnob: Missing GPU resource cleanup on unmount (Impact: MEDIUM)
**Severity**: Medium  
**Evidence**: Effect cleanup only calls `cancelAnimationFrame(animationId)`. No `device.destroy()`, `context.unconfigure()`, or buffer release.  
**Cost**: Memory leak in the GPU process. Repeated mount/unmount cycles (e.g., tab switching, conditional rendering) will accumulate orphaned GPU allocations until the page is refreshed.

### 4. 🟡 Knob.tsx: `useCallback` over-subscription causes effect churn (Impact: LOW-MEDIUM)
**Severity**: Low-Medium  
**Evidence**: `handleMouseMove` depends on `[isDragging, dragStartY, dragStartValue, min, max, step, onChange, logarithmic]`. When drag starts, `isDragging` flips → callback ref changes → `useEffect` in lines 79–93 tears down and re-adds global `mousemove`/`mouseup` listeners on every drag start/end.  
**Cost**: DOM listener churn on every drag interaction. With 20+ knobs, this is negligible in practice but avoidable.

### 5. 🟢 Knob.tsx: No actual layout reflow (Impact: NONE / MISCONCEPTION)
**Severity**: None  
**Evidence**: The only animated CSS property is `transform`, which is compositor-only. No `width`, `height`, `top`, `left`, `margin`, or `padding` changes.  
**Cost**: Zero layout recalculation. The browser handles rotation entirely on the compositor thread.

### 6. 🟢 useStableKnobConfig: Dead code for primary Knob.tsx sites (Impact: NONE)
**Severity**: None  
**Evidence**: `SynthPart.tsx` and `DrumMachine.tsx` do not import or use `useStableKnobConfig`. It is only consumed by `useAppState.tsx` for `HardwareModule`.  
**Cost**: No runtime penalty; purely a code-health note.

## Recommended Fixes

### Fix 1. Share a single GPU device + pipeline across MagicKnob instances (Scoped: `MagicKnob.tsx` or new `KnobGpuContext`)
- Extract adapter/device request to a module-level singleton promise.
- Cache the `GPURenderPipeline` and `GPUShaderModule` at module scope (or in a React context) so all instances reuse one compiled pipeline.
- Each instance only needs its own `canvas`, `canvas context`, `uniformBuffer`, and `bindGroup`.
- **Expected impact**: Eliminates redundant shader compilation and device creation. Reduces RAF loops from N to 1 if further merged into a single shared renderer, or at least reduces per-instance overhead to ~O(1) buffer updates.

### Fix 2. Add dirty-checking + visibility pause to MagicKnob RAF (Scoped: `MagicKnob.tsx`)
- Track `prevValueRef` and `prevTimeRef`. If `value` is unchanged and `time` has not advanced meaningfully (> 16 ms for animation), skip the render pass submission.
- Use `IntersectionObserver` to pause RAF when the canvas is off-screen (`isIntersecting === false`).
- Use `document.visibilityState` to pause when the tab is hidden.
- **Expected impact**: Reduces GPU workload from 100% duty cycle to only frames where visual change is required.

### Fix 3. Proper GPU teardown on unmount (Scoped: `MagicKnob.tsx`)
- In the effect cleanup, add:
  ```ts
  if (device) { device.destroy(); }
  if (context) { context.unconfigure(); }
  ```
- **Expected impact**: Prevents GPU memory leaks during component lifecycles.

### Fix 4. Merge multiple MagicKnobs into a single canvas (like HardwareModule) (Scoped: architectural)
- Follow the pattern in `HardwareModule.tsx`: one canvas, one pipeline, one uniform buffer with an array of knob positions/values, rendered in a single draw call.
- **Expected impact**: Reduces N RAF loops to 1, N fragment passes to 1, and eliminates per-instance WebGPU context overhead entirely.

### Fix 5. Fix Knob.tsx listener churn (Scoped: `Knob.tsx`)
- Restructure drag listeners so they are attached once at mount (or on `mousedown`) and removed on `mouseup`, without depending on `isDragging` in the `useEffect` dependency array.
- Use refs for `dragStartY` and `dragStartValue` instead of state, or move listener attachment into the `mousedown` handler.
- **Expected impact**: Eliminates `useEffect` re-runs and DOM listener churn during drag.

### Fix 6. Audit orphaned MagicKnob (Scoped: product / codebase health)
- `MagicKnob.tsx` is not imported by any production file. Either delete it to reduce maintenance burden, or integrate it behind the `is3D` flag in `HardwareModule.tsx` where the shared renderer already exists.
- **Expected impact**: Removes dead code and prevents accidental adoption of a high-cost component.

---

## Status: complete

**Summary**: The audit found that `MagicKnob.tsx` — despite being orphaned in production — contains severe latent performance issues: per-instance GPU device creation, per-instance shader compilation, unconditional RAF loops with no dirty-checking, and missing GPU teardown. If mounted, even a single instance would waste significant GPU/CPU resources. The production knob (`Knob.tsx`) is actually well-behaved: it uses compositor-only `transform` animations, is memoized, and does not force layout reflow. The primary DOM-side risk is minor listener churn during drag interactions. `useStableKnobConfig` is dead code for the main Knob.tsx consumers but correctly serves `HardwareModule`. A minimal `engineTelemetry.recordLatency('knob-raf', ...)` probe has been added to `MagicKnob.tsx` so that if it is ever mounted, the Engine HUD (`Ctrl+Shift+E`) will surface per-frame render timing.
