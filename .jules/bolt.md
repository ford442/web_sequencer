## 2026-06-25 - Real-time Polyphonic Closure Hoisting
**Learning:** During polyphonic granular playback (`useAudioEngine.ts` inside `playSamplerVoice`), defining complex closures like `triggerVoice` and `runVoices` inside the `notes.forEach` loop forces the engine to re-allocate and capture these heavy functions for every note triggered. In glitch effects or wide chords, this creates intense garbage collection overhead per frame.
**Action:** Always identify and hoist closures out of high-frequency inner loops. Pass dynamic iteration variables (like `noteStr`) as explicit parameters instead of capturing them implicitly, fully decoupling the logic from the inner loop execution phase and avoiding per-note memory reallocation.

## 2026-06-30 - Vocoder AudioNodePool Optimization
**Learning:** In `useAudioEngine.ts`, allocating complex `AudioWorkletNode` instances like `vocoder-processor` on every polyphonic note trigger causes significant main-thread garbage collection (GC) overhead and potential audio dropouts. Additionally, setting a `useRef` to `null` is not enough to pool it; it must be explicitly initialized with `new AudioNodePool(context, ...)` inside `initializeAudio` after the module is loaded. Without this, `pool.acquire()` fails and falls back to `new AudioWorkletNode()` every time.
**Action:** Always explicitly initialize `AudioNodePool` references inside `initializeAudio` (making sure to pass necessary options like `{ numberOfInputs: 2 }` for the vocoder). Use `poolRef.current?.acquire(parameterData)` during triggers and `poolRef.current?.release(node)` instead of `.disconnect()` during teardown to correctly recycle Worklet nodes and eliminate per-note allocations.
