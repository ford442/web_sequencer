## 2024-04-26 - [Avoid Stale Closures When Memoizing Many Handlers]
**Learning:** When trying to memoize a large set of event handlers (like dozens of onChange handlers for Knobs) to prevent child re-renders, relying directly on prop dependencies in `useCallback` defeats the purpose as it creates a new function reference every time the prop changes.
**Action:** Use the `useRef` + `useEffect` pattern (or a `useLatest` hook) to hold the latest value of the frequently changing prop (like `params`), so the `useCallback` dependency array can be empty (or only rely on stable setters) while still accessing current data.
## 2026-04-28 - [React.memo Optimization for Static/Simple Components]
**Learning:** Wrapping basic functional UI components that don't depend on deeply nested or rapidly changing contextual states with `React.memo()` prevents unnecessary React reconciliation overhead whenever the top-level app state changes. However, when doing bulk syntax migrations (like automating the insertion of `React.memo`), AST-based tools like `jscodeshift` are vastly superior to naive regex matching, which is prone to missing closing braces or breaking standard imports.
**Action:** Use AST codemods (like `jscodeshift`) rather than Regex for bulk component refactors. Add `React.memo()` directly to exported functional components (`React.FC`) that are visually heavy or state-agnostic (like Canvas wrappers) to improve rendering performance.
## 2026-05-01 - [FastAPI GZip Middleware Optimization]
**Learning:** Returning large, uncompressed JSON payloads (like songs/patterns) from a FastAPI backend wastes bandwidth and increases load times. FastAPI includes a built-in `GZipMiddleware` that can be added in one line to compress these payloads efficiently.
**Action:** When building backend APIs that return large JSON datasets, always add `GZipMiddleware(minimum_size=...)` near the top of the middleware stack (before CORS) to reduce payload size without manual compression logic.
## 2026-05-06 - [Avoid Pure Rendering Violations with useRef]
**Learning:** Using the `useRef` + `useEffect` pattern to store frequently changing properties (like event handlers or configurations) to optimize `useCallback` dependency arrays works well, but reading `ref.current` *during the React render phase* violates pure rendering rules. It results in stale closures (lagging one render behind) and breaks the component's visual state.
**Action:** Restrict reading `propsRef.current` strictly to event handlers (like `onClick`, `onMouseMove`) or side effects (like `useEffect`). Never access it inside functions that return JSX or calculate rendering state outside an effect.
## 2026-05-06 - [Avoid Layout Thrashing with ResizeObserver]
**Learning:** Calling \`getBoundingClientRect()\` inside a \`requestAnimationFrame\` loop or a high-frequency \`mousemove\` handler causes "Forced Synchronous Layout" (Layout Thrashing), severely degrading performance.
**Action:** Instead of reading \`getBoundingClientRect()\` directly during interactions, use a \`useRef\` to store a cached \`DOMRect\` and keep it updated using a \`ResizeObserver\` attached to the element. This ensures the layout is only calculated when the element actually resizes, completely eliminating overhead during dragging and animation.
## 2026-05-07 - [Memoize Expensive Inline Array/Object Creation in Frequently Rendered Components]
**Learning:** Components that handle gestural inputs (like dragging) trigger many re-renders. If they generate arrays or perform string/color lookups inline during the render cycle (like iterating octaves or generating a Set of scale notes), it degrades performance.
**Action:** Always wrap these inline calculations in a `useMemo` hook with correct dependencies so they are only recalculated when their specific inputs (like min/max bounds or current scale) change, rather than on every single pixel dragged.

## 2025-05-18 - [React.memo Optimization for appParts Components]
**Learning:** Top-level UI structural components like `KeyboardNode`, `SequencerNode`, `RackNode`, `TransportHeader`, and `ContextMenuNode` were defined as `React.FC` but were missing `React.memo()`. While some of these connect deeply via `useAppState()`, wrapping them in `React.memo()` is a best practice to avoid unnecessary render evaluation cycles when the parent `App` or surrounding contexts re-render with stable props. Note that `React.memo` returns a `MemoExoticComponent`, which does not have a callable signature compatible with `React.FC`. Therefore, when applying `React.memo()` to these exports, the explicit `: React.FC` typing on the variable must be removed to prevent TypeScript compilation errors (`Type 'NamedExoticComponent<object>' is not assignable to type 'FC<{}>'`).
**Action:** Consistently apply `React.memo()` when defining large structural components. Use AST codemods (like jscodeshift) for safer global refactors, and ensure `: React.FC` annotations are stripped from variables receiving `React.memo()` wraps to maintain TS build integrity.
## 2026-05-13 - [Avoid Redundant DOM Updates on Audio Ticks]\n**Learning:** When a UI component updates its classList based on a fast-firing audio scheduler tick (e.g., via `setHighlight` every 16th note), it's crucial to guard the DOM mutation with a check to ensure the state has actually changed. If `newActiveIndex === lastActiveIndexRef.current` but `classList.add` is repeatedly called inside an `else` block, it forces the browser to process a style recalculation on every tick, causing significant layout overhead during playback.\n**Action:** Always check if the tracked index has changed before attempting to add or remove classes. Remove any redundant `else` blocks that re-apply the same class, and apply this pattern consistently across all sequencer rows and playhead components.

## 2024-05-18 - [Stabilize Event Handlers to Fix React.memo Re-render Cascades]
**Learning:** When attempting to prevent massive re-renders in a grid of memoized components (like a sequencer), simply overriding `areEqual` to ignore changing event handlers causes a severe "stale closure" bug, as the child holds onto the initial, outdated handler and state.
**Action:** Always address re-render cascades at the source: stabilize the event handlers in the parent component. Use the `useRef` + `useEffect` (or `useLayoutEffect`) pattern to cache rapidly changing state variables (e.g., `isDrawing`, `selection`, `activeTrack`), allowing the `useCallback` dependency array to be empty. This maintains a stable function identity for `React.memo` to work correctly while ensuring the handler always accesses the freshest state when executed.
## 2024-05-11 - Custom `areEqual` for Heavy Sequencer Grids
**Learning:** Even when using `React.memo` and `useCallback` on handlers passed from parent components, complex UI matrices (like the 256-step grid in `MainSequencer` or 32-step arrays in `SequencerRow`) can still suffer from re-render cascades if the parent has transient state (like `isDrawing` or selection bounds) that causes function references or props to update frequently during high-frequency events (like playback or mouse movement).
**Action:** When working with massive arrays of child components (like `SvgStep` or sequencer rows), wrap them in `React.memo` and supply a custom `areEqual` function that strictly compares *only* the data properties (like `stepIndex`, `active`, `note`, `length`) and ignores event handlers entirely. For arrays or objects within those props, use `JSON.stringify` or deep equality checks to prevent unnecessary DOM diffing.
